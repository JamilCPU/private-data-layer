# Step 5: sms-store, the phone SMS forwarder and sms-mcp — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Texts received or sent on the owner's phone become searchable through the assistant within a minute: an Android app forwards them to an in-cluster receiver that writes to the Lab Data Store, and a read-only MCP backend exposes them behind the gateway.

**Architecture:** Three pieces. `servers/sms-store` (`pdl_sms_store`) is a small Starlette service with one write endpoint, `POST /messages`, authenticated by a per-device bearer token (stored hashed, minted by a helper); it writes to Postgres schema `sms` as `sms_owner`, applies its own migrations, and is the only piece with an Ingress besides the gateway and the assistant (`sms.lab`, TLS from the lab CA). `servers/sms-mcp` (`pdl_sms`) mirrors email-mcp: FastMCP, shared-secret middleware, reader role, tools `search_sms` and `list_recent_sms`. `apps/sms-forwarder` is a Kotlin/Compose Android app (same conventions as the Personal Automations app) that pairs with the store through a `pdl-sms://pair?...` URI, pins the lab CA by fingerprint, forwards new texts from a receiver and a periodic content-provider sweep, resolves contact names on the phone, queues while offline, and shows a status screen. Persistence follows the Lab Data Store conventions used in step 3.

**Tech Stack:** Python 3.12, Starlette/uvicorn, httpx, psycopg 3, `mcp>=1.30,<2`, pytest + respx + asgi-lifespan; Kotlin 2.x, Jetpack Compose (BOM 2024.12), Ktor client (OkHttp engine), WorkManager, Room, DataStore, JUnit; Gradle 8.9 wrapper, Android SDK 35 on the primary node (`/opt/android-sdk`, JDK 21); k8s manifests as in steps 3 and 4.

**Spec:** `docs/superpowers/specs/2026-11-02-private-data-layer-design.md` sections 5.2 (`sms-mcp` + `sms-store`, common rules), 7 step 5, 8, 9; the Lab Data Store tenant conventions (schema per source, `<src>_owner` writes and migrations, `<src>_reader` reads, Secret `lab/lab-data-store` keys `SMS_OWNER_PASSWORD`/`SMS_READER_PASSWORD`, host `postgres.lab.svc.cluster.local:5432`, db `lab`).

## Global Constraints

- `sms-store` accepts only `POST /messages` with a valid device token and `GET /healthz`; everything else is 404; the Ingress routes only those two paths. Request body is JSON, at most `MAX_BODY_BYTES = 65536`, at most `MAX_BATCH = 100` messages per request; each message body at most `MAX_TEXT_CHARS = 2000` characters (longer is cut and marked). Per-token rate limit `60` requests per minute (429). Tokens are stored hashed (PBKDF2, same helper style as the gateway's `pdl-new-client-secret`), compared in constant time, never logged.
- Message id = `sha256(f"{device}|{provider_id}|{date_ms}")[:32]`; inserts are `ON CONFLICT DO NOTHING`; re-posting a batch adds nothing.
- `sms-mcp` is read-only, `/mcp` behind `X-Gateway-Secret`, `/healthz` open, tool descriptions one or two plain sentences for a 32B model, `ToolAnnotations(readOnlyHint=True, destructiveHint=False, openWorldHint=False)`; rows carry `id, contact, address, direction, sent_at, body` with `body` capped at `BODY_RETURN_MAX = 500` characters; search is a case-insensitive substring over body, contact and address; defaults `limit=20`, max `100`.
- Phone app: permissions `RECEIVE_SMS`, `READ_SMS`, `READ_CONTACTS`, `INTERNET` only; no cleartext traffic; TLS trust is the pinned lab CA fingerprint from the pairing URI (`fp`), hostname verified normally against the leaf; the device token lives in DataStore encrypted with an Android Keystore key (same pattern as the Personal Automations app); contacts are resolved on the phone and only the name is sent, never the full contact record; nothing is sent until paired.
- Public repo: no hostnames, addresses, secrets or personal data in code, tests or docs (`*.lab` and service names allowed in `deploy/` and in the app's example pairing text); fixtures synthetic.
- Frozen dataclasses, type hints, functions ≤ 50 lines, files ≤ 400, logging not print, TDD, coverage ≥ 80 (`pyproject` gate), `filterwarnings = ["error"]`, ruff clean; Kotlin: ktlint-style formatting, unit tests for the pure logic (pairing parse, id derivation, batching, contact lookup mapping), no network in tests.

## Review Focus

1. `POST /messages` with a wrong, missing or revoked token, or a token for another device: 401 before the body is parsed, with no detail about which part failed; the rate limiter counts failures too. Test in Task 2.
2. A batch with 101 messages, a 70 KiB body, a message body of 5,000 characters, a non-JSON body, a JSON object instead of a list, a message missing `provider_id`: 413/422 with a one-line reason, nothing stored from a rejected batch (all-or-nothing per request). Test in Task 2.
3. The phone forwards the same text twice (receiver + sweep): one row, `duplicates: 1` in the response; the app's queue marks it done either way. Test in Tasks 1 and 6.
4. `search_sms` with a contact filter that matches nobody, a `since` in the future, or a query of one character: empty list, never an error; a query of only whitespace behaves like `list_recent_sms`. Test in Task 3.
5. The phone is offline for an hour: texts queue locally, the next upload sends them oldest first in batches of at most 100, and a 401 (token revoked) stops uploads and shows "not paired" instead of retrying forever. Test in Task 6.

### Task 1: sms-store models, device tokens, stores and migrations

**Files:** `servers/sms-store/pyproject.toml` (name `pdl-sms-store`; deps `starlette`, `uvicorn[standard]`, `pyyaml`, `psycopg[binary]`; scripts `pdl-sms-store = pdl_sms_store.__main__:main`, `pdl-sms-new-device-token = pdl_sms_store.cli_tokens:main`; pytest config as email-mcp), `uv.lock`, `src/pdl_sms_store/{models,tokens,cli_tokens,store,memory_store,postgres_store,migrations,store_factory}.py`, `migrations/001_sms.sql`, tests `test_models`, `test_tokens`, `test_cli_tokens`, `store_cases`, `test_store_contract`, `test_postgres_store`; CI job `sms-store` with the Postgres service (copy of `email-mcp`).

**Interfaces:**
- `Message(id, device, provider_id: str, thread_id: str | None, address: str, contact: str | None, direction: Literal["in","out"], body: str, sent_at: datetime, received_at: datetime)` frozen; `message_id(device, provider_id, date_ms: int) -> str`; `parse_incoming(device: str, raw: dict, received_at: datetime) -> Message` validating keys `provider_id` (str), `date_ms` (int ≥ 0), `address` (str, 1..64), `contact` (str | None, ≤ 128), `direction` (`in`/`out`), `body` (str; cut to `MAX_TEXT_CHARS` with `truncated` noted by appending ` [truncated]`), `thread_id` (str | None); bad → `ValidationError(field, reason)`.
- `tokens.py`: `hash_token(token) -> str` (`pbkdf2_sha256$200000$salt$digest`, reuse the gateway's format), `verify_token(token, hashed) -> bool` constant-time, `load_device_tokens(path) -> Mapping[str, str]` (YAML `devices: {name: hash}`; empty or missing → `TokensError`), `find_device(token, devices) -> str | None` (checks every entry; constant work per entry). `cli_tokens.py`: `pdl-sms-new-device-token --name <device> [--out FILE]` generates a 32-byte urlsafe token, writes it to `--out` (0600, refuses overwrite) or prints it once to stdout, and prints the YAML line `  <name>: <hash>` to stderr for the tokens file.
- `Store` Protocol: `upsert_messages(msgs) -> int` (new count), `record_device_seen(device, at, last_provider_id) -> None`, `count() -> int`; `MemoryStore`; `PostgresStore(dsn)` with `apply_migrations` (schema guard + advisory lock + per-file transactions as in step 3), `store_from_env` (`SMS_STORE=memory|postgres`, `SMS_APPLY_MIGRATIONS`, `PG*` defaults), `StoreConfigError`.
- `001_sms.sql`: schema `sms` (guarded `DO` block), `sms.messages(id text PK, device text, provider_id text, thread_id text, address text, contact text, direction text CHECK (direction IN ('in','out')), body text, sent_at timestamptz, received_at timestamptz, tsv tsvector GENERATED ALWAYS AS (to_tsvector('simple', coalesce(contact,'') || ' ' || coalesce(address,'') || ' ' || coalesce(body,''))) STORED)` with indexes `(sent_at desc)`, `(address)`, GIN on `tsv`, unique `(device, provider_id, sent_at)`; `sms.devices(name text PK, last_seen_at timestamptz, last_provider_id text)`; guarded grants to `sms_reader` (as step 3).

### Task 2: sms-store HTTP app, entrypoint, image

**Files:** `src/pdl_sms_store/{app,__main__}.py`, `tests/{test_app,test_main}.py`, `Dockerfile`, `.dockerignore`, `README.md`.

**Interfaces:**
- `build_app(store: Store, devices: Mapping[str, str], *, now: Callable[[], datetime] = utcnow, rate: RateLimiter | None = None) -> Starlette`; routes: `GET /healthz` → `{"ok": true}`; `POST /messages`: requires `Authorization: Bearer <token>` → device name via `find_device` else 401 `{"error": "unauthorized"}` (before reading the body); content-length / body > `MAX_BODY_BYTES` → 413; body must be a JSON list of 1..`MAX_BATCH` objects else 422 `{"error": "<reason>"}`; each parsed with `parse_incoming` (first failure → 422, nothing stored); then `new = store.upsert_messages(msgs)`, `store.record_device_seen(device, now(), max provider_id)`; 200 `{"accepted": new, "duplicates": len(msgs) - new}`; any other path/method → 404. `RateLimiter(limit=60, window_s=60, clock=time.monotonic)` keyed by device name, counting every request incl. failures; over → 429 with `Retry-After`. Security headers as the assistant uses; JSON only; no cookies; log one INFO line per request with device, count, status, never the body.
- `main()`: env `SMS_STORE_LISTEN_HOST/PORT` (0.0.0.0/8000), `SMS_DEVICE_TOKENS_FILE` (required), `SMS_STORE` / `SMS_APPLY_MIGRATIONS` / `PG*`; config errors → stderr `sms-store: ...` exit 1.

### Task 3: sms-mcp package

- `search_sms(query: str, since: str | None = None, contact: str | None = None, limit: int = 20)` — "Search the owner's text messages by words in the message, the contact name or the number, optionally since an ISO 8601 time or from one contact. ### Task 6: Android app: SMS reading, receiver, contacts, queue, upload worker

**Files:** `sms/{SmsReader,SmsReceiver,ContactResolver,Queue,UploadWorker}.kt`, Room entities/DAO for the queue (`queued_messages(provider_id PK, date_ms, address, contact, direction, body, thread_id, state, attempts)`), tests `SmsReaderTest` (cursor mapping with a fake cursor), `QueueTest` (Room in-memory via Robolectric or a pure-Kotlin queue abstraction with a fake DAO), `UploadWorkerTest` (batching, ordering, 401 handling with fakes).

**Interfaces:**
- `SmsReader.readSince(contentResolver, sinceDateMs: Long, lastProviderId: Long?): List<RawSms>` over `content://sms` (`_id`, `thread_id`, `address`, `date`, `type` (1 inbox → `in`, 2 sent → `out`; other types skipped), `body`), ordered by `date`; `ContactResolver.name(contentResolver, address): String?` via `PhoneLookup` with an LRU cache; `Queue.enqueueAll(items)` (ignore duplicates by `provider_id`), `nextBatch(limit = 100)` oldest first, `markSent(ids)`, `markFailed(ids)`, `pendingCount()`.
- `SmsReceiver` (`SMS_RECEIVED_ACTION`): extracts the messages, enqueues them with `provider_id = "rx-<timestamp>-<hash>"`? No: the receiver only triggers an immediate sweep (`UploadWorker.enqueueNow`), so every text has the content-provider `_id` as its `provider_id` and the sweep is the single source of truth (dedupe stays simple).
- `UploadWorker` (WorkManager `CoroutineWorker`, periodic every 15 minutes with network constraint, plus one-off runs from the receiver and the "Sync now" button): sweep → enqueue → upload batches oldest first until the queue is empty or a failure; `Unauthorized` → clear the paired token's "valid" flag, stop, status shows "not paired"; `Failed` → retry with WorkManager backoff; records last result in DataStore. Review Focus 3 and 5 pinned by tests with fakes.
